## 三、各节内容设计

### 6.1 系统转换（重点★★★★）

**核心内容**：

新旧系统之间的过渡方式，4 种典型策略对比（必考）：

| 转换方式 | 工作原理 | 风险 | 成本 | 适用场景 |
|---------|---------|------|------|---------|
| **直接转换** | 旧系统停 → 新系统起 | 高 | 低 | 小型/非关键系统 |
| **并行转换** | 新旧系统同时运行一段时间 | 低 | 高（双倍） | 关键系统、大型业务 |
| **分段转换** | 按模块/功能逐步切换 | 中 | 中 | 复杂系统、可分模块 |
| **试点转换** | 部分用户/部门先用 | 低-中 | 中 | 多分支机构、地理分散 |

**关键 callout**：
- `> [!important]` 4 种转换方式对比表（必背）
- `> [!tip]` 题目区分：看到「核心业务、不能停」 → 并行；看到「分批 / 模块」 → 分段；看到「先选试点」 → 试点

### 6.2 数据迁移与备份恢复（次重点★★★）

**核心内容**：

**数据转换与迁移**：
- 数据清洗：去重、修正、补全、标准化
- 数据转换：格式 / 编码 / 单位 / 业务规则映射
- 数据装载：批量 / 增量
- ETL 流程：抽取（Extract）→ 转换（Transform）→ 装载（Load）

**备份策略**（3 种 + 增量 vs 差异区别）：
- **完全备份**：备份全部数据，恢复快、占空间多
- **增量备份**：只备份"自上次任意备份以来"变化的数据，备份快、恢复慢（需依次叠加）
- **差异备份**：只备份"自上次完全备份以来"变化的数据，备份中等、恢复中等（只需最近一次完全 + 一次差异）

**关键 callout**：
- `> [!important]` 3 种备份策略对比表
- `> [!warning]` 易混点：增量是"自上次备份"、差异是"自上次完全备份"
- `> [!tip]` 备份策略选择：要恢复快选差异 / 要节省空间选增量

### 6.3 系统维护（重点★★★★）

**核心内容**：

**4 类维护**（必考、考频高）：

| 类型 | 英文 | 触发原因 | 工作内容 | 占比（参考） |
|------|------|---------|---------|------------|
| **改正性维护**（纠错） | Corrective | 发现既有缺陷 | 修复 bug | 约 21% |
| **适应性维护** | Adaptive | 外部环境变化（OS/硬件升级） | 适配新环境 | 约 25% |
| **完善性维护** | Perfective | 用户提出新需求/性能改进 | 增强功能、优化性能 | 约 50%（最高） |
| **预防性维护** | Preventive | 为提高未来可维护性 | 重构、优化代码结构 | 约 4% |

> 占比口诀：**改 21、适 25、完 50、预 4**（完善性占比最高，约一半）

**维护性度量（5 个子特性）**：
- **可理解性（Understandability）**：理解软件的容易程度
- **可测试性（Testability）**：测试软件的容易程度
- **可修改性（Modifiability）**：修改软件的容易程度
- **可移植性（Portability）**：移到其他环境的容易程度
- **可重用性（Reusability）**：被复用的容易程度

**维护成本因素**：模块独立性、应用领域复杂度、文档质量、人员稳定性、编程语言

**关键 callout**：
- `> [!important]` 4 类维护对比表 + 占比口诀（最常考）
- `> [!warning]` 易混：改正性 = bug 修复；预防性 ≠ bug 修复（前置工作，让代码更好维护）
- `> [!tip]` 关键字判定：「修复缺陷」→改正性；「OS 升级 / 硬件更换」→适应性；「新需求 / 优化」→完善性；「重构 / 增强可维护性」→预防性

### 6.4 系统评价（了解）

**核心内容**：
- **系统评价**：对运行中的系统进行综合评价，决定是否保留 / 改进 / 替换
- 三个评价维度：
    - **绩效评价**：系统运行性能（响应时间、吞吐量、可靠性）
    - **效益评价**：经济效益（节约成本、提升效率）
    - **安全评价**：安全性、合规性
- 评价时机：上线后 3-6 个月、年度评价、重大变更前后

**关键 callout**：
- `> [!note]` 系统评价是系统全生命周期的"反馈环节"，结果驱动维护或更新决策

### 6.5 系统演化与再工程（重点★★★★）

**核心内容**：

**遗留系统 4 象限演化策略**（必考，业务价值 vs 技术水平）：

```
              业务价值高
                  │
          淘汰    │    集成
   技术━━━━━━━━━━━┿━━━━━━━━━━━ 技术
   水平          │            水平
   低     继承   │    改造     高
                 │
              业务价值低
```

| 象限 | 业务价值 | 技术水平 | 策略 | 含义 |
|------|---------|---------|------|------|
| **淘汰**（左上） | 高 | 低 | 弃旧建新 | 价值高但技术老旧，建议重新开发 |
| **集成**（右上） | 高 | 高 | 集成进新系统 | 价值高技术也行，集成到企业总体架构 |
| **继承**（左下） | 低 | 低 | 维持运行 | 价值低技术老，做最小维护 |
| **改造**（右下） | 低 | 高 | 升级改造 | 价值低但技术新，改造提升业务价值 |

> 注：业务价值和技术水平的"高低"在不同教材有时反向标注，但 ==落地策略名是固定的==（淘汰/集成/继承/改造）。

**软件再工程**：

软件再工程 = ==逆向工程 + 重构 + 正向工程==

抽象层次详细推导参见 [[05-软件工程概述#逆向工程]]：
- 实现级（最低）→ 结构级 → 功能级 → 领域级（最高）

**关键 callout**：
- `> [!important]` 4 象限演化策略表（必考）
- `> [!warning]` 4 象限的策略名固定，不要被"高/低"位置混淆
- `> [!note]` 软件再工程 = 逆向工程 + 重构 + 正向工程（重写）；详细 4 抽象层次见 [[05-软件工程概述]]
